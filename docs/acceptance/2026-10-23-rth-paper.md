## Order acceptance

- A pending one-contract entry with protection was repriced through the actual
  chart. With One-click off, a draft survived normal polling and Discard sent no
  request. Confirm sent one price amendment. One-click release sent one amendment.
  The parent and both unfilled children were subsequently confirmed canceled.
- A default, unprotected option entry filled. A pending Add was dragged from 1.60
  to 1.71. The request journal recorded an acknowledged amendment after the
  broker-open-order check. Cancel targeted that Add only; cancellation eventually
  reconciled while the original filled position remained one contract.
- A subsequent Add filled, increasing the test position to two. Trim filled one
  contract, leaving one. Manual TP/SL were then installed and modified through
  the chart: SL draft/Discard/Confirm and One-click TP each preserved the expected
  submission behavior. Close filled and both protection orders were canceled.
- A separate two-contract position received TP and SL of quantity two. Close
  canceled both protection orders and filled both contracts. The three initial test
  groups ended flat with every order Filled or Cancelled.

Options intentionally default to **no TP/SL**. IB restrictions prevent Add/Trim
with the manually attached option protection used here. The observed disabled
controls are expected behavior, not a defect or an invitation to change the
baseline. This run does not claim protected-option Trim/resizing acceptance.

The initial automated entry-drag attempts did not hit an editable line: one
snapshot was stale, and the far-away test limit later fell outside the visible
price range. After waiting for fresh state and making the line visible, actual
mouse interaction passed. No broker write resulted from those missed gestures.

Several order submissions initially returned an unknown/awaiting-broker outcome.
They were reconciled by request ID without replaying writes. Some read requests
returned `QUEUE_FULL`/503 and recovered. Helper request-to-confirmed-state times
ranged from about 1.7 to 14.6 seconds; this includes broker reconciliation and
read retries and is not exchange latency. The pending Add cancellation exceeded
the UI harness's bounded wait before later reaching Cancelled. No claim is made
that queue saturation or all long-tail latency has been eliminated.

## Deployed request scheduling evidence

Read-only analysis of existing Mini request diagnostics, 21:33–22:03 Shanghai,
identified all 18 test order POSTs. All returned HTTP 200 (which is not a promise
of broker acceptance). Owner-queue wait ranged from **0.4 to 206.6 ms**. In three
observed cases, an order started before an earlier-arriving bootstrap read while
an already-running pending-orders read completed first. This corroborates deployed
write priority without preempting the active IB operation. The exact pending-history
ordering remains covered by the existing controlled executor evidence, not by
claiming a history/POST race that this live sample did not capture.

The same window contained 121 read 503 responses: 103 latest-chart reads, four
history reads, five execution reads, two profile reads, four order-state reads,
two volatility reads, and one EMA read. This is a count over the observed workload,
not a failure percentage or an A/B comparison. The response/queue diagnostics
separate brief order admission waits from longer broker-outcome reconciliation.
They do not prove every reconciliation delay originates at IB. No diagnostic
configuration or service was changed, and no extra order was submitted for this
analysis.

submitted well below the current bid, without TP/SL. Older QQQ history was requested
and a price plus DAY-to-GTC edit was sent. The history requests completed before
the order POST reached the owner (last history completion 22:16:07.125; order start
22:16:07.878 Shanghai). Therefore this attempt is **not** evidence of a queued
history request being overtaken by the order. It did exercise the surrounding
history workload and order handling while chart packets were sampled.

cancellation-confirmation window. It returned unknown and later reconciled to
canceled, with no replacement, no fill, and no remaining order. This matches the
existing late-cancel safety rule: a later GET must not submit the replacement.
It is evidence of safe uncertainty recovery, **not a successful TIF amendment**.
The placement and edit queued for 9.5 and 5.9 ms respectively; the latter spent
4,247.7 ms inside its owner job. The extra test group also finished flat. Its
read-only option quote subscription automatically closed after two minutes.
