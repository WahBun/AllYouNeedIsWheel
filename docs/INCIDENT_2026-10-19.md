## BE stop amendment

A BE stop added to an entry-only option group is stored in the group's `ids.sl`.
The entry lots still contain only their entry IDs. Price amendment code selected
the lot path whenever lots existed, so it could not find the aggregate stop.
Eight persisted stop-drag requests failed with `Exit order is no longer working`.
The BE result had reported the stop as `PreSubmitted`.

Use the exact group stop identity when `manual_stop_quantity` is set. Preserve
existing reconciliation, amendment confirmation, order terms and no-replay guards.
REA process capture verified the persisted group-level stop and entry-only lots.
The regression reproduces the original rejection, then checks recovery, one
amendment with unchanged identity/quantity, no replay and cancellation rejection.
134 related mock tests passed; broker acceptance remains unverified.

## Opening delays

Chart-opening requests at 21:45:56 and 21:47:28 China time spent approximately
15 seconds executing, then returned 503. The same pattern occurred after the
operator's restart. Opening-hour logs also contain numerous queue-full rejections.
Cold chart history uses synchronous IB history requests on the serialized owner.
This establishes slow chart loading and queue pressure, but does not establish
the full cause of reported tick latency: ticker callbacks can publish during
yielding IB reads. Do not replace or throttle the protected tick delivery path
based on queue timings alone.

Initial chart history now waits asynchronously on the same IB event loop, with
at most two pending reads and bounded retained results. HTTP returns a loading
response promptly. Web and native clients wait without treating that response
as a price snapshot; the web releases its per-page read admission between polls.
No extra IB owner, quote throttle, tick aggregation or order retry was introduced.
Account/client changes discard late results and release unclaimed option history.
Request timing excludes time spent waiting for a client to consume the result.

An isolated Flask regression holds two history responses while other requests
and an existing chart's tick callbacks continue. A real browser regression loads
four delayed chart snapshots and verifies all four resume continuous updates.
The paired steady-state 1/2/3/4-pane, two-page/four-pane and long-history tests
measured source-to-chart-apply p95 of 3–9 ms both before and after (synthetic input).
Layout/reconnect, 100 Hz stress and eight-distinct-symbol checks also passed.
This removes the observed cold-history bottleneck; upstream broker latency and
the next real market opening remain unverified until deployment and observation.

## Performance history and intraday updates

The inspected cache contained account data through October 16 and S&P 500 data
through October 16, but NASDAQ 100 only through October 15. Curves use the common
date intersection, so the API returned October 15 as its end date. Its six-hour
cache was marked fresh. This is a backend data/alignment limitation, not evidence
that the phone failed to receive a newer curve.

New native requests opt into independent account dates. Missing index values stay
null; legacy clients retain their numeric payload. Delayed benchmarks retry after
five minutes, explicit Refresh is bounded, and the visible page rereads history.
Benchmark download failures retain the latest account history and available index
observations. No dates or values are fabricated and no production cache or
database was modified during development.

The existing five-second live account-P&L loop and intraday return formula remain.
NDX's missing final point no longer truncates the account history or disables that
estimate. Model tests cover stale P&L and session restrictions. A hosted native
page with mock P&L changed from +14.80% to +10.88% on the next live read while NDX
remained missing. This is simulator evidence, not a broker fill or device test.
